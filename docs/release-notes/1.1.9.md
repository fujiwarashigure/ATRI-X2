# ATRI-X 1.1.9 发行说明

1.1.9 有三条互不相干的改动线，**都不改配置格式、工具 schema、会话 / 数据库格式**：

1. **上下文窗口在桌面端可配置**：新增「模型 → 上下文窗口」子页，可以改默认窗口、按
   Provider + 模型覆盖，并能一次扫描上游 `/models`，把全部模型与上游上报的理论窗口列进
   「模型窗口总览」表，直接在表里点单元格设自定义覆盖。
2. **`/resources` 统计子进程**：除了 ATRI-X 自身进程，还把软件拉起的子进程（DSH 内核
   `node.exe`、draw.io 渲染链、研究 runner、agent 启动的 shell / MCP / hook 等）与同安装
   目录的相关进程（桌面端、QQ 协议端）一起统计内存与 CPU，并给出「合计」。
3. **内置 DSH 可在桌面端配置**：新增「DSH」选项卡，把原先只能手改 `app.toml` 的
   `[agent.dsh]`（路由 / 凭据 / 内核模型目录）做成表单，带凭据诊断、状态刷新与端到端自检；
   换机器或重装后点一次「一键配置」即可恢复。

配置向后兼容：1.1.8 的 `app.toml` / `services.toml` / `state.toml` 原样可用；本版只读写
`services.toml` 与 `app.toml` 里**本来就存在**的字段，没有新增配置项，也不需要迁移数据。

## 一、上下文窗口：从"只能手改 TOML"到桌面端可配可扫

**旧状态（1.1.8）**：chat / work 的上下文窗口只能手改 `services.toml` —— 要么动全局回退值
`[model_metadata].default_context_window`（默认 `256000`），要么给单个模型写
`[providers.<name>.model_configs."<model>"].context_window`；桌面端「模型」页没有入口。
上游窗口比 256K 大的模型（例如 OpenCode Go 的 `deepseek-v4.1-flash`，其 `/models`
元数据里的 `limit.context` 是 1,000,000）在后台读不到上游元数据时会被按 256K 预算提前
压缩，长会话吃亏，而普通用户很难自己写出正确的覆盖键。

**新状态（1.1.9）**：

- **默认窗口**：桌面端「模型 → 上下文窗口」子页顶部可以改默认窗口，保存写
  `[model_metadata].default_context_window` 并回读 `services.toml` 校验。
- **按模型覆盖**：同一页可以按 provider + model 设 `model_configs.<模型>.context_window`；
  已有覆盖在「按模型覆盖」表里展示，可点选回填、可删除；保存后同样回读校验。
- **模型窗口总览**：点「扫描上游窗口」会对该 Provider 的 `GET /models` 发一次请求
  （兼容 `.../openai/v1` 这类网关把清单挂在服务根下的情况，例如 OpenCode Go 的清单在
  `{服务根}/v1/models`），把**全部模型**与上游上报的理论窗口（`limit.context` 等字段）列进
  表里；上游没上报窗口的模型也会列出（显示「—」），不会漏模型。
- **表格内直接改**：「自定义覆盖」列可以点击单元格修改（回车保存 / Esc 取消 / 失焦也保存），
  保存即写 `model_configs.<模型>.context_window` 并回读校验；「删除所选覆盖」撤掉覆盖；
  底部保留一行手打模型名保存覆盖的入口（扫描没覆盖到的模型也能设）。
- **全部 Provider**：Provider 下拉支持「全部 Provider」，一次扫描所有配置过的 Provider；
  失败项逐条报错、成功的照常入表。扫描结果缓存在配置目录的 `gui/model_catalog.json`，
  重启桌面端后表格仍然可见（「重新载入」只重读配置，不重新发请求）。
- **口径不变**：窗口解析顺序仍是「Provider 上报元数据 → 按模型覆盖 → 默认窗口 → 内置
  `256000`」，上游自己上报的窗口仍然最权威；本页只在上游没上报 / 后台读不到时兜底。
  改完是**启动期配置**，需要在桌面端「重启后台服务」后生效。

## 二、`/resources`：从"只看自己"到"看整个软件"

**旧状态（1.1.8）**：`/resources`（以及模型侧的 `runtime_resources` 工具）只报 ATRI-X
**自身那一个进程**的 RSS / CPU / 线程 / 句柄。任务管理器里由软件拉起来的 `node.exe`
（DSH 内核）、`draw.io.exe`（图表渲染链）、研究 runner、GUI（`atri-x-gui.exe`）与 QQ 协议端
（`NapCatWinBootMain.exe` / `QQ.exe`）都不在统计里，手机上看资源占用会严重低估。

**新状态（1.1.9）**：新增 `atri_x/sysinfo_children.py`，一次快照额外采两组进程，并按两次
采样求 CPU（单核基准）：

- `【子进程】`：当前后台服务的**子孙进程**（DSH 内核、draw.io 渲染链、研究 runner、
  agent 拉起的 shell / MCP / hook 等），按可执行文件名聚合出内存 / CPU；
- `【相关】`：与 ATRI-X **同安装目录**的其它进程（桌面端、QQ 协议端、渲染残留；只在冻结
  安装版采集，源码树跑测试不会误扫无关进程）；
- `【合计】`：软件自身 + 子进程 + 相关进程的总体占用（RSS 为各进程相加，共享页会重复计算）；
- 空闲时明确显示"无活动子进程（DSH 内核 / 渲染器等按需启动）"，不会让人误以为功能坏了。

实现口径：Windows 用 `ctypes` 调 kernel32 的 Toolhelp 快照 + `OpenProcess`（零第三方依赖），
Linux 读 `/proc`；采集失败只写进 `【降级】`，不会让 `/resources` 整条失败。隐私边界不变：
明细只出现**可执行文件名**（如 `node.exe`、`draw.io.exe`），不出现命令行、路径、用户名；
`runtime_resources` 的 JSON 结果新增 `children` / `related` / `software_total` 三个字段。

## 三、内置 DSH：从"只能手改 TOML"到桌面端可配可自检

**旧状态（1.1.8）**：`[agent.dsh]` 与内置内核的模型目录补丁
（`DSH_HOME/profiles/acp/cordis.patch.yml`）在桌面端**没有任何入口**，只能手改文件。后果有
三类：① 缺 `[agent.dsh]` 时凭据自动落到 work provider（常见是 OpenAI 兼容网关），被协议
判定为不可用，表现为"深度路由从没生效"；② 网关提供的模型 id 与内核自带目录不一致时，
`session/prompt` 直接 400；③ 换机器 / 重装后只能重新翻文档手改，容易漏。

**新状态（1.1.9）**：桌面端新增**「DSH」选项卡**（`atri_x/gui/tabs/dsh.py` +
`dshpanels.py`，数据层 `dshconfig.py` / `dshcatalog.py` / `dshsmoke.py`；「功能」页的
「内置 DSH 深度路由」行双击也能跳过去）：

- **路由**：启用、`min_score`、预热、并发上限、空闲回收、单轮超时、会话复用；保存写
  `app.toml` 的 `[agent.dsh]`，走行级补丁 + `.gui.bak` + 回读严格解码。
- **凭据**：Provider 下拉 + 协议下拉，选中即诊断（`base_url` 是否 Anthropic Messages 端点、
  密钥是否已配置、声明了几个自定义请求头）；不是 Messages 端点时给出「同一网关的
  Anthropic 地址」建议并可一键复制。
- **内核模型目录**：按所选 Provider 的 `models` 生成 `cordis.patch.yml`（上下文窗口取
  「模型 → 上下文窗口」页的值），旧文件备份为 `.gui.bak`；也可清空（回内核自带目录，
  官方 DeepSeek 密钥场景用）。
- **状态与自检**：「刷新状态」等价于 `atri_x.agent.dsh.status`；「端到端自检」真的拉起内核
  跑一轮 `session/prompt`，把 `stopReason` / 回答 / 内核 stderr 尾部显示在页面上。
- **一键配置（推荐）**：选 Provider → 生成内核模型目录 → 写 `[agent.dsh]` → 询问重启，
  换机器或重装后点一次即可恢复（端点不兼容时先弹确认，不静默强改）。
- **顺带修掉的真实缺陷**：ACP `session/set_config_option` 的 `model` 取值必须是**紧凑
  JSON**（`["<provider>","<model>"]`，逗号后不能有空格），带空格会被内核判
  `[-32602] unknown model option`；页面写入时统一规范化，避免手改配置踩坑。

这些仍是**启动期配置**，保存后需要点「重启后台服务」才生效；`min_score` 默认 0.40，
简单对话不走 DSH 属预期行为。

## 四、升级与兼容

| 项 | 说明 |
|---|---|
| 配置格式 | 不变（`app.toml` / `services.toml` / `state.toml` 原样可用） |
| 会话 / 数据库 | 不变，无需迁移 |
| 工具 schema | 不变；`runtime_resources` 只在 JSON 结果里新增字段 |
| 桌面端页签 | 顶部**追加**一个「DSH」页（排在最后），既有页签、按钮与保存行为不变 |
| 生效方式 | 上下文窗口与 `[agent.dsh]` 改完需「重启后台服务」；`/resources` 立即生效 |
| 安装版 | 直接覆盖安装 1.1.9，配置与会话数据不用动 |
| 便携版 | 解压到新目录，把旧目录的 `data\` 拷过去即可继续用 |

回滚：安装版装回 1.1.8 即可（配置与会话格式未变）；便携版解压 1.1.8 后指回旧 `data\`；
源码树切回上一版源码。回滚后 `services.toml` 里新增的窗口覆盖与 `app.toml` 的
`[agent.dsh]` 仍会被 1.1.8 正常读取（字段本就存在），只是没有 GUI 编辑入口；
「DSH」页生成的 `cordis.patch.yml` 会保留，旧版内核照读，想回内核自带目录在页面点「清空」。

## 六、已知限制（如实说明）

- 上游 `/models` 不一定带窗口字段、清单也不一定挂在 API 根下；后台读不到时以「按模型覆盖」
  或「默认窗口」为准，扫描表里的「上游上报」列只作展示参考。
- `/resources` 只按**可执行文件名**聚合，同名多进程会合并计数；RSS 是各进程相加，共享内存
  会重复计算，`【合计】`不是去重后的物理占用。
- DSH 内核 / draw.io 是按需启动的：没有跑深度任务或图表渲染时 `【子进程】` 为空是正常的。
- 「DSH」页的凭据诊断是**静态判断**（端点形状 / 密钥是否存在 / 请求头声明），不联网校验
  密钥有效性；真正可用性以「端到端自检」为准。Provider 没声明 `models` 时无法生成内核
  模型目录，页面会提示先补 `models`。
- 未连接真实平台服务端（QQ / Telegram 只有进程内假连接用例）；未调用真实模型 API。
